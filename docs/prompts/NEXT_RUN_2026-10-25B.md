# Next run — the residual surface, and the thing the bootstrap cannot fix

Verified since the last report: the `34` is correct and partitions cleanly (`expected` 34 ∪ `revoked` 15 = the snapshot's 49 anon grants, disjoint — checked mechanically, not by eye). The assertion file is a real pin now. Two corrections below, then the item that matters.

## 1. Move the `psql` check below every refusal

`run-nulls-preflight.sh:39` tests `command -v psql` before the Supabase host policy at line 49. On a machine without psql, `scripts/db-tests/run-nulls-preflight.test.mjs` cases 3 and 4 fail with `CANNOT PROVE: psql is not installed` instead of the `REFUSED` message they assert — 2 of 4 pass here, 4 of 4 only where psql exists.

A capability check must not mask a policy decision, and a fail-closed test whose result depends on ambient tooling is not evidence. Move the `command -v psql` guard to immediately before the first connection, after every refusal. The suite must then be 4/4 on a machine with no PostgreSQL client at all.

Two smaller things in the same file:

- The first connection captures `2>&1` into `OBSERVED`, so under `set -e` a failure exits with the server's message discarded. The operator sees a bare non-zero status. Print `$OBSERVED` before exiting.
- The header logs `inet_server_addr()` as `# target_host`. That is a private IP, not the name the operator chose; two Supabase projects can share one. `HOST` is already computed at line 46 and is password-free — log it as `# target_hostname` alongside the observed address.

## 2. Assert the property, not only the census

Set equality over explicit `anon` entries is correct and should stay. But a function with `proacl IS NULL` has `EXECUTE` to `PUBLIC` and never appears in that census — which is why `public_default_anon_exec=152` is a NOTICE rather than a failure. The security property is not "34 functions carry an anon entry"; it is "anon cannot execute a `SECURITY DEFINER` function outside the documented 34".

Add one hard assertion: for every `SECURITY DEFINER` function in `public` whose `oid::regprocedure::text` is not in the 34, `has_function_privilege('anon', oid, 'EXECUTE')` must be false. Name each violation. Report the count of non-definer functions anon can reach via `PUBLIC` separately — that number is expected to be large and is not the finding.

Do not pin `public_default_anon_exec` to a number. It moves whenever an extension or a migration adds a function, and it is not the property.

## 4. The item the bootstrap cannot fix — decide it, do not implement it

`canonical_public_schema.sql:26325` is a dump of production's own default ACL:

```
ALTER DEFAULT PRIVILEGES FOR ROLE "postgres" IN SCHEMA "public" GRANT ALL ON FUNCTIONS TO "anon";
```

with the same for `SEQUENCES` at 26315 and `TABLES` at 26335. That is why the snapshot re-grants anon after `db-reset-fresh.sh` removes it, and why the six migration-created functions carried anon entries.

The bootstrap change fixes the disposable build. **Production still carries that default.** Consequence: every function the migration chain creates in production is anon-executable unless something revokes it, and every table created there is granted `ALL` to anon unless RLS plus a revoke says otherwise. The six known functions — `clinical_documents_protect_signed()`, `death_pronouncements_protect_signed()`, `_grant_hospital_cap(text,text,text,text,text)`, `profiles_guard_privileged_columns()`, `set_intake_case_tenant_from_owner()`, `set_intake_message_tenant_from_case()` — are evidence the generator is live, not the whole of it.

I checked the eleven post-cutoff tables that have no literal `ENABLE ROW LEVEL SECURITY`: all eleven are covered by the dynamic loops at `20260921120000_pharmacy_purchases.sql:154` and `20261022160000_pharmacy_accounting_ledger.sql:969`. No table is exposed today. Record that check so nobody repeats it.

Do not write the remediation. Produce a one-page decision memo at `docs/decisions/PRODUCTION_DEFAULT_PRIVILEGES_2026-10-25.md` covering:

- What the live default grants today, to which roles, on tables, sequences and functions.
- The blast radius of revoking the table default specifically — which app or PostgREST paths read tables as `anon` and would break.
- Whether the remedy is a migration (repeatable, reviewable, applies to every environment) or operator DDL (immediate, unrepeatable, must be re-derived by hand for staging).
- The ordering constraint: this must not sit in the same change as the tenancy policy repair, because a failure in one must not roll back the other.

Nothing in this section is applied, and nothing is applied to any remote database.
